# Итоговая сверка КР №3

## Бизнес-правило приоритета

Завершённая или отклонённая заявка имеет NORMAL. Остальная срочная — URGENT. PROCESSING без срочности — HIGH. Остальные — NORMAL. Правило совпадает в DTO, SQL-фильтре и аналитической группировке; проверяется тестами.

Отключённые/архивные сектора не принимают новые назначения заявок. Существующая заявка не теряет связи и доступность. Место с заявками нельзя перенести в другой сектор: 409 защищает согласованность прямой связи заявки со справочником.

## Проверки

- Локальный `gradlew.bat test` на H2 включает старые сценарии и CourseworkCompletionTest.
- `scripts/verify-compose.ps1` собирает код в Docker и поднимает изолированный PostgreSQL 17.
- `scripts/verify-live.cjs` проверяет health, временный пароль/вход, version/409, метки, комментарии, фильтры, частичный bulk, CSV по внешнему коду, аналитику, аудит, OpenAPI, refresh и отзыв после выхода.
- `scripts/verify-persistence.cjs` проверяет сохранение заявки и изменённого пароля после обычного compose down/up.

Проверочный проект использует отдельную базу/volume и порт 18081, не очищает основную базу и не выводит секреты. Последний локальный запуск: **69 тестов, 0 failures, 0 errors**. HTML-отчёт: build/reports/tests/test/index.html.

Фактический итоговый Docker-прогон также завершился успешно: образ собран из актуальных исходников, PostgreSQL и backend получили статус healthy, HTTP acceptance прошёл, после обычного down/up сохранились заявка и изменённый пароль администратора. Проверялись в том числе refresh и невозможность пользоваться access JWT после выхода. Тестовый стек оставлен работающим на localhost:18081; основной volume проекта не менялся.

## Сценарий защиты

1. Запуск docker compose up --build --wait, показать оба healthy сервиса и /actuator/health.
2. Войти, показать обязательную смену временного пароля и различия WORKER/MANAGER/ADMIN.
3. Создать клиента, сектор, место и заявку; показать code/title/urgent/priority/version/updatedAt.
4. Изменить заявку с версией, повторить старую версию и получить 409.
5. Показать поиск, фильтры, сортировку и страницы; затем метки и закреплённый служебный комментарий.
6. Выполнить bulk со смешанным успехом и ошибкой; архивировать и восстановить заявку.
7. Экспортировать CSV, проверить файл, применить по внешнему code и показать ошибки строк.
8. Показать сводку аналитики, управление сотрудниками и журнал аудита с Correlation ID.
9. Показать Swagger, таблицы/версии Flyway и сохранение данных после down/up.

JavaFX из КР №2 остаётся отдельным клиентом, Android относится к КР №4. Результат этого проекта — backend КР №3, как сформулировано в скриншоте. Для старого клиента массивы списков сохранены, но обновления должны передавать текущую version.
